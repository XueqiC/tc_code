# T–C 边界对齐:gradient → spectral 路线的方法草图

日期:2026-08-09(用户重构问题后第一版)
状态:讨论稿,未与用户确认

## 1. 问题表述(capability shaping via distillation)

给定:
- 大 LLM agent(teacher)π_T,以**代码**作为行动空间完成任务;
- k 个 few-shot query,Q = {q_1, …, q_k},k ∈ 几 ~ 几百,隐式定义一个 topic/task 域 T。

求一个方法,输出:
1. **边界估计器** B: query → {in, out},从 Q 学得,对新 query 判断是否属于 T,
   带统计保证(conformal 覆盖);
2. **蒸馏出的小模型** π_S,使基于它的 agent 的能力边界 C 与 T 对齐:
   - **覆盖**(T ⊆ C):q ∈ T 时,π_S 成功率 ≈ π_T(或高于阈值);
   - **收紧**(C ⊆ T,capability shaping):q ∉ T 时,π_S 不具备该能力
     (失败/拒绝),不为域外能力浪费容量。

核心难点:T 是由 query 语义隐式给出的,C 是模型参数的性质——它们天然不在
同一个空间里,"对齐"无从度量。**本方法的中心思想:把 T 和 C 放进同一个空间
——梯度空间——使对齐成为可度量、可优化的几何量。**

## 2. 统一空间:query 的梯度特征

每个 query q 先由 teacher 跑出代码轨迹 τ(q)(agent 的行动即代码,轨迹天然
承载了任务所需的 tool/API 使用、控制流、数据流)。在参考模型 θ(student 的
base,或一个固定 probe 模型)上计算

  g(q) = ∇_θ ℓ(τ(q); θ)

即"让这个模型学会该轨迹所需的参数移动方向"。工程上用 LESS 式做法压成本:
LoRA 参数上的梯度 + 随机投影降到 d 维(d ~ 8192),L2 归一。每条 query 一次
反传,便宜。

这个表示的含义:**一个任务 = 一族参数空间中的移动方向**。两个 query 属于
同一任务 ⇔ 学它们要求模型往相近的方向移动。这比语义 embedding 更贴近
"能力"的本体——它是关于*学*这个任务的,不是关于*描述*这个任务的。

## 3. 任务边界 T:谱子空间 + conformal 半径

1. 对 {g(q_1), …, g(q_k)} 求协方差 Σ = (1/k) Σ_i g_i g_iᵀ;
2. 谱分解,取 top-r 特征向量张成**任务子空间** U_T(r 由谱能量占比或
   held-out 重构误差选);
3. 新 query q′ 的隶属度分数:
     s(q′) = ‖U_Tᵀ g(q′)‖ / ‖g(q′)‖   (投影能量比)
4. 在 Q 的留一/split 上做 conformal 校准得阈值 t_α → 判别器
   B(q′) = [s(q′) ≥ t_α],带 (1−α) 覆盖保证。

"stack" 的层级化(用户点到的方向,待展开):
- **逐层子空间**:梯度按 transformer 层分块,每层各得一个 U_T^(l);浅层可能
  编码格式/语法,深层编码任务语义——stack 起来得到一个层级化的边界描述,
  也是可解释性卖点(哪一层的子空间在区分这个任务?)。
- **逐轨迹步**:代码轨迹按步骤(每个 code block / tool 调用)切开分别算梯度,
  子空间的并/加权和描述任务的"技能组成"——与原稿的结构坐标
  (tool closure / composition / dataflow)可以互相印证,但不再依赖手工定义。
- **多子空间混合**:k 大时先对 {g_i} 聚类再分别取子空间,边界 = 子空间并集,
  容纳多模态任务域。

## 4. 能力边界 C:同一空间里的残差梯度

student θ_S 在 query q 上的**残差梯度** g_S(q) = ∇_{θ_S} ℓ(τ(q); θ_S):
- ‖g_S(q)‖ 小(且实际执行成功)⇔ 已掌握该 query;
- **C 的操作性定义**:残差梯度范数低于阈值的 query 区域。

于是 T–C 对齐有了几何度量:
- **覆盖缺口**:E_{q∈T} ‖g_S(q)‖(或在 U_T 内的分量)——还没学会的方向;
- **泄漏**:域外 query 上 student 的成功率 / 残差下降量——多学了的方向;
- **子空间对齐**:U_T 与"训练前后参数实际移动方向的主子空间"的主角
  (principal angles)。

## 5. 蒸馏控制:让 C 贴合 T

- **数据侧(主)**:候选蒸馏数据(teacher 轨迹,可由 Q 出发让 teacher
  self-generate 扩增)按 s(·) 选择/加权——只用投影能量比高的样本;
  这是 LESS 式 data selection 换了目标:不是选"对 val 集有用的",
  而是选"落在任务子空间内的"。
- **更新侧(可选,更强)**:训练时把梯度更新投影回 U_T(或惩罚 U_T 外分量)
  ——直接抑制域外能力增长。这一步是方法上的新东西,需要消融验证
  不伤域内学习。
- **容量侧(观测)**:固定 T,扫 student 大小,看"恰好满足 T 的最小容量"
  ——capability shaping 的效率叙事。

## 6. 必须诚实面对的问题

1. **C ⊆ T 受 base 先验限制**:蒸馏只能*增加*能力,base 小模型本来会的
   域外能力删不掉。域外抑制的可行手段:(a) 选先验最小的 base;(b) 蒸馏时
   混入域外拒绝数据(行为层抑制,不是能力删除);(c) unlearning;
   (d) agent 层 gating(用 B 做前置过滤——但这算系统方案,不是模型方案)。
   论文里应把 "capability" 与 "behavior" 的区分写清楚,主张只做到哪一层。
2. **梯度特征对参考模型的依赖**:g(q) 取决于在哪个 θ 上算。需要验证
   子空间结构对 θ 的选择(student base vs probe)稳健,或干脆固定用
   student base(最贴近最终用途)。
3. **轨迹非唯一**:同一 query teacher 可采样多条轨迹,梯度会漂。
   多采样取均值/取子空间并,或按成功轨迹过滤。
4. **长轨迹的信用分配**:整条轨迹一个梯度太粗;逐步梯度(§3 的 stack)
   既是精化也是解药。
5. **与语义 embedding 基线的对照必须做**:如果 sentence embedding + 同样的
   conformal 流程就能判边界,梯度空间的必要性就不成立。预期优势场景:
   语义相近但所需能力不同(同 topic 不同工具深度)、语义不同但能力同构。
   实验设计要专门构造这两类对照。

## 7. Pilot(rai 可做,不烧大卡)

目的:验证第一步(边界估计)成立,方法才立得住。
1. 选 2–3 个 topic 的 agent 任务(用现成 tool-use benchmark 的子集,或
   自建代码 agent 任务),每 topic ~50 query;
2. teacher(API 大模型)生成代码轨迹;
3. 在一个小 base(1–2B, LoRA)上算梯度特征;
4. 验证:(a) 谱子空间能否分开 topic(子空间主角、聚类纯度);
   (b) 投影能量比 + conformal 能否判别 held-out query 的 in/out,
   与 semantic-embedding 基线对比;
   (c) k 从 5 → 50 → 200 的样本效率曲线。
通过 → 再设计蒸馏侧实验(hpg)。
