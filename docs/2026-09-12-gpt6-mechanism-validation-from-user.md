**建议先做一轮“6 个训练任务＋3 个基座评测”的单卡实验：每个 benchmark 只比较“普通局部练习”和“针对学生缺口的专项练习”。** 先确定针对性是否有效，再补完整轨迹等对照。

这轮不运行复杂的在线门控、QP 或 meta-gradient。所有训练采用相同的软目标蒸馏，只改变教师怎样生成练习，以便干净地验证：

> **同样的教师预算和训练曝光，针对学生具体困难生成的短交互练习，能否改善未见完整任务？**

以下按 **BFCL＋ALFWorld＋HotpotQA**、教师 **GPT-5.6-luna**、学生 **Gemma-4-12B-it**、一张 **A100 80GB** 设计。

**一、先把实验规模固定下来**

| 项目                     | 首轮配置                                         |
| ---------------------- | -------------------------------------------- |
| 每个 benchmark 的 support | 24 个任务                                       |
| 独立训练校准任务               | 16 个，计入 few-shot 数据访问量                       |
| 训练种子                   | 1 个，两个实验臂配对使用                                |
| 每个 benchmark 的训练臂      | 普通局部练习 C、专项练习 D                              |
| 共享诊断及准备预算              | 最多 8k 教师输出 token                             |
| 每臂材料生成预算               | 最多 24k 教师输出 token                            |
| 首轮总教师预算上限              | \(3\times(8k+2\times24k)=168k\) output token |
| 训练方式                   | BF16 LoRA＋固定学生软目标保留                          |
| 模型输出                   | 每个 benchmark 独立 adapter，不混合训练                |

预算是建议的探索规模，不要求花满。记录真实 model ID、模型版本和 usage；生成、修复、失败尝试及计费 reasoning 都计入。不能只计算最后留下来的示范。

**本轮只允许这 40 个任务参与发现问题、调试和校准。** 正式评测题不能进入教师出题 context。

---

**二、三个 benchmark 使用同一个机制，但各自提供不同的证据**

| Benchmark | 首轮重点验证                    | 固定评测                      |
| --------- | ------------------------- | ------------------------- |
| BFCL      | 条件变化后，是否正确改变调用、参数或调用顺序    | 预先固定的 256 题分层子集           |
| ALFWorld  | 局部操作学会后，是否能在长任务中正确触发并继续执行 | `valid_seen` 140 题，作为开发评测 |
| HotpotQA  | 局部证据连接训练，是否改善完整多跳问答       | 官方 dev 中预先固定的 256 题       |

**BFCL：** 使用官方 checker，覆盖参数绑定、调用／不调用、并行调用和多轮状态。Support 与评测按父任务和函数家族隔离。如果从官方评测集中抽取 support，就必须把这些题及其相关生成后代排除，首轮结果称“机制验证子集”，不能冒充官方 Overall。[BFCL 数据说明](https://huggingface.co/datasets/gorilla-llm/Berkeley-Function-Calling-Leaderboard)

**ALFWorld：** 使用现有文本环境和相同 harness，完整任务上限建议先沿用已有 40 步协议。训练练习来自 train 的合法状态与重放，不能让教师虚构房间、物品状态或环境返回。`valid_seen` 是开发集，后续独立确认另行进行。[ALFWorld 官方实现](https://github.com/alfworld/alfworld)

**HotpotQA：** 优先使用现有 agent harness。若尚未搭好，采用本地、固定的工具化 distractor 设置：`search`、`read`、`finish`，搜索范围是题目给定的十个段落，不使用实时互联网。报告 Answer EM/F1，并在输出格式支持时报告 supporting-fact F1；明确这是工具化 distractor 协议。[HotpotQA 官方设置](https://hotpotqa.github.io/)

这样可以避免 HotpotQA 退化为“把所有材料一次塞给模型做普通 QA”，也避免外部搜索变化污染结果。

---

**三、先运行基座，找到少量真实缺口**

每个 benchmark 先让 Gemma 在 24 个 support 任务上运行一次，保存完整轨迹和检查结果。

从中选择**最多 8 个失败情境**作为出题种子，尽量覆盖不同父任务。选择只根据 support，不看正式评测结果。

可能发现的情境包括：

| Benchmark | 候选缺口示例，不是预设规则                     |
| --------- | --------------------------------- |
| BFCL      | 参数缺失时仍然调用；参数已齐却弃答；没有使用上一轮返回值      |
| ALFWorld  | 达成某个物品状态后，不知道下一步操作；重复执行已完成动作      |
| HotpotQA  | 找到第一跳实体后没有继续检索；用相邻实体的属性回答；证据不足就结束 |

教师根据轨迹提出**可检验的缺口假设**，同时指出支持它的具体行为。不要让教师直接输出“缺乏规划能力”这种无法验证的大标签。

如果 Gemma 在某个 support 集上几乎全部成功，应报告这个测床缺少学习空间。不要从正式评测里不断找错题来补齐。

---

**四、核心对照：相同上下文，只有“出题是否针对缺口”不同**

这是本轮最重要的控制。

| 项目             | C：普通局部练习      | D：专项练习         |
| -------------- | ------------- | -------------- |
| 任务目标、工具接口、起始状态 | 相同            | 相同             |
| 学生错误及诊断信息      | 不提供           | 提供             |
| 生成要求           | 生成这个局部阶段的多样练习 | 围绕具体决策缺口生成多样练习 |
| 输出格式、长度要求、预算   | 相同            | 相同             |
| 环境验证           | 相同            | 相同             |
| 蒸馏方法           | 相同            | 相同             |

这样，D 对 C 的收益才能归因于**学生相关的专项教学**，而不是 D 获得了不同工具、更干净状态或更多训练材料。

每臂目标为约 **48–96 个有效练习**，但教师 token 上限优先，不为凑数量超预算。

D 的练习不能只是改实体名，应同时包含：

* 改变关键条件，正确动作随之改变；
* 改变表面信息，正确决策关系保持；
* 学生原来正确的邻近情境，避免学成单侧反射。

例如 BFCL 的同一接口，既练习“参数缺失，需要澄清”，也练习“参数齐全，应正常调用”。这正好针对我们此前观察到的调用／弃答偏移。

**不强行要求每个失败都能构造严格对照对。** 做不到的记录下来，不能为了凑对而生成不自然或不可执行的数据。

---

**五、练习必须接近真实 agent 输入**

每条练习至少保存：

```text
父任务及来源
学生可见的任务与历史
工具接口、环境快照或文档集合
教师的短示范
实际执行结果与验证状态
教师成本
训练/评测分组标识
```

特别强调三个细节：

1. **学生看不到诊断标签。** 不给它写“这题考察缺失参数”或“现在需要第二跳检索”。
2. **局部练习结束不等于整个任务结束。** 只结束监督范围，不伪造 `finish`、EOS 或任务完成动作。
3. **验证允许不同正确解。** 不要求学生逐字复现教师的代码或调用序列。

ALFWorld 优先复用合法环境状态；HotpotQA 使用真实训练文档生成有依据的问题，答案和隐藏验证信息不进入学生输入。

首轮由教师生成、环境或 checker 验证。**教师批改暂不加入主对照**，否则会同时改变数据与反馈资源。

---

**六、A100 80GB 上的训练方案**

Gemma 官方模型卡列出约 11.95B 参数和约 262k 词表。BF16 权重本身约 24GB，但激活、logits 和训练缓存还会占用显存，因此需要 LoRA 和分块软目标计算。[Gemma 模型卡](https://huggingface.co/google/gemma-4-12B-it)

建议起始配置：

| 参数                           | 设置                                  |
| ---------------------------- | ----------------------------------- |
| 权重精度                         | BF16，不先引入量化变量                       |
| LoRA                         | rank 16，alpha 32，dropout 0          |
| 训练模块                         | 解码器 attention 和 MLP 的适用线性层，按实际模块名核对 |
| 学习率                          | `1e-5`，首轮所有臂一致                      |
| Micro-batch                  | 1                                   |
| Gradient checkpointing       | 开启                                  |
| 上下文                          | 常规 4k，确有必要的完整上下文走 8k                |
| Teacher/student soft mixture | 固定 0.5／0.5                          |
| Reference                    | 冻结的原始 Gemma                         |
| Thinking                     | 显式固定；若无既有协议，首轮关闭，所有臂一致              |
| 训练与推理服务                      | 分时使用 GPU，不同时常驻                      |

参考分布可以通过**关闭 adapter 的同一底座**计算，不需要再加载一个 12B 模型。

完整词表软目标按位置分块计算，不能长期缓存每条样本所有位置的巨大概率矩阵，也不能把 top-k 近似悄悄称作完整分布。原生 chat template 和工具解析需要先通过小规模检查。

训练曝光建议这样控制：

* C、D 各使用最多一遍有效数据。
* 取两臂都能提供的共同监督 token 数，上限先设 **16k**。
* 按累计监督 token 进行梯度累积，保证损失归一化一致。
* 不为了达到步数，把少量短练习重复十几遍。
* 未训练到的已购买数据仍计入教师支出。

同时记录输入 token、监督 token、更新步数和实际运行时间。等教师成本与等 GPU 成本是不同问题，不能混为一谈。

首轮不以“训练越久越好”为目标；若监督损失明显下降而完整任务退化，应先分析迁移或干扰。

---

**七、评测必须区分“专项题会做”和“完整任务变好”**

每个训练模型做三层评测：

| 层次          |              建议规模 | 判断内容            |
| ----------- | ----------------: | --------------- |
| 未见局部练习      | 约 48 个，按父任务／生成组留出 | 是否掌握了局部条件关系     |
| 自然上下文中的继续执行 |     约 24 个独立训练侧状态 | 是否无需诊断提示也会使用    |
| 完整任务        | 前面固定的 benchmark 集 | 是否真正改善 agent 表现 |

第二层作为诊断，不能代替第三层。它使用的状态也不能与训练练习同源泄漏。

正式评测使用同一 A100、同一生成参数、同一 harness。首轮采用 greedy，先验证基座重复执行是否稳定；若环境本身有随机性，固定并记录环境 seed。

每个题都保存配对结果：

* C 错、D 对；
* C 对、D 错；
* 两者都对／都错；
* 工具调用次数、非法动作、重复动作、提前结束。

统计按独立任务或父任务组计算配对区间。几十个来自同一 seed 的变体不能当作几十份独立证据。

---

**八、单卡执行顺序与时间控制**

推荐依次执行：

1. **兼容性检查**：模型加载、工具格式、参考软分布、一个训练步和 adapter 重放。
2. **基座 support rollout**：三个 benchmark 各 24 个任务。
3. **教师生成与 CPU 验证**：生成 C、D，教师 API 不占 A100。
4. **BFCL 的 C、D 训练与评测**：先得到最快的机制信号。
5. **ALFWorld、HotpotQA 的 C、D**：相同机制继续测试。
6. **汇总六个模型的局部与完整任务配对结果。**

目标是把首轮控制在**约一天量级的 GPU 时间**，但这不是已测时长。先测 10 个训练步和一小批完整任务，再按实际吞吐估算剩余时间；长程 rollout 很可能比训练更耗时。

为节省时间，先不跑 BFCL 全量、不加第二种 loss、不扫多组 LoRA 配置，也不进行训练中频繁全套评测。

---

**九、什么结果值得进入下一轮？**

首轮结果可以这样判断：

| 结果                         | 下一步                   |
| -------------------------- | --------------------- |
| D 的局部与完整任务都优于 C，且不是单个父任务贡献 | 补完整轨迹与原位置短指导对照        |
| D 只改善局部练习                  | 检查自然触发、上下文差异和后续衔接     |
| C、D 都改善且接近                 | 有效的是局部练习或多样性，尚未证明针对性  |
| D 修复目标行为但损伤其他行为            | 检查单侧训练、条件覆盖与保留强度      |
| C、D 都没有学动                  | 检查监督有效性和曝光，不能直接否定专项机制 |

若出现清楚的正向信号，再在一个 benchmark 上补两个训练臂：

* **A：完整教师轨迹**；
* **B：原失败位置的短示范，使用相同训练曝光重复学习**。

此时才能进一步确认：收益来自“针对缺口的多样练习”，而不仅是局部纠正；并检验它是否在相同教师预算下优于完整示范。

**这轮最重要的产物是一张明确的机制表：同一学生、同一工具、同一预算、同一蒸馏目标，加入学生缺口信息后，教师出的小练习是否让完整任务表现提高。** 六个训练任务足以开始回答这个问题，也适合当前的一张 A100。
