## 一、BFCL:修复终止监督后的四种子重跑

### 1.1 为什么要重跑
9 月 12 日下午的三项实现核查发现一个真实缺陷:渲染监督目标时,原生的工具交接标记 `<|tool_response>`、
回合结束标记 `<turn|>` 与 `<eos>` 被**主动剥掉**,编码阶段也没有补回,保存的 `compatibility.json` 里写着 `no_terminal_supervision: true`。
影响范围:R1 的 C/D 各 22/22 条全部缺失交接监督;R2 的 C 56/59、D 56/61。
另两项核查无问题:冻结参考分布确实来自未截断全词表、温度 T=1,不继承评测解码;两臂曝光匹配。

**表述口径(按评审)**:该缺陷与"重复输出同一工具调用直到 4096 token 上限"的塌缩形态相符,**但尚未单独建立因果**;
旧结果保留为受缺陷影响的历史观测,既不能否定机制,也不能反推修复后 D 就会有效。

### 1.2 执行
同一批 R2 练习、同样剂量、修好的目标渲染,**无新教师调用**;base + C/D 各四个训练种子 = 9 个作业并行,每臂独立 run 目录。
剂量:LoRA r16/α32,AdamW lr 1e-4,512 监督 token/步,目标 = 0.5 教师 one-hot + 0.5 冻结 base 全词表。

### 1.3 曝光分项(八臂,`exposure-audit`)
| 臂 | 内容 token | 工具交接 | 回合结束 | 合计 | 步数 |
|---|---:|---:|---:|---:|---:|
| C 种子 0–3(四臂一致) | 15,850 | 560 | 30 | 16,440 | 40 |
| D 种子 0 / 1 / 2 / 3 | 15,923 / 15,921 / 15,922 / 15,918 | 473 / 474 / 474 / 478 | 44 / 45 / 44 / 44 | 16,440 | 40 |

总监督曝光八臂完全相同;内容曝光相差 ≤73 token(0.46%);边界组成有小幅不对称(C 更常以工具调用结束,D 更常以文本回合结束),如实记录,不称"完全匹配"。
另:修复后内容曝光与修复前的总量同为 15,850,即**终止监督是额外加上去的 590 个 token**,并未挤占内容曝光;
但它仍改变了目标组成、归一化分母与梯度相对贡献,所以修复前后的差异**不能**完全分解为"边界语义"与"优化变化"。

### 1.4 结果
| 臂 | 四个种子(/246) | 均值 | 局部 (33) | 续接 (9) | 确认集 (16) |
|---|---|---|---|---|---|

|---|---|---|
| base → C | +1.19 | [−1.36, +3.99] |

**结论**:修复终止监督**没有改变机制结论**——靶向练习相对通用练习无稳定优势,局部层与确认集不动。
**唯一明确改善的是训练稳定性**:修复前 D 跨种子极差 8 题且出现过一次塌缩;修复后极差 6 题、四个种子**无一塌缩**。

## 二、HotpotQA(ReAct 工具检索版)测床合格性

### 2.1 这个 harness 到底是什么
逐行确认:`src/bfas/hotpotqa.py` 是 ReAct 循环——模型自己写 `Thought n:` / `Action n:`(search / lookup / finish),
环境返回 `Observation n:`,受 MAX_STEPS 约束;检索是 ReAct 原版 Wikipedia HTTPS 包装器,带不可变的按查询磁盘快照缓存。
题目来自 distractor 划分,但**交互协议是自主检索**,不是"一次性喂十段文档"。supporting-facts 仅用于评估与审计,不进学生上下文,
也不把合法的替代检索路径判错。base:EM 38.2 / F1 47.8(500 题 dev),平均 4.75 步。

### 2.2 三轮检查与两次自我纠错
- **v1(离线缓存)**:20 题里 14 题因缓存缺页失败,数字反映缓存覆盖而非模型能力,作废。→ 改为实时检索。
- **v2(实时检索,24 题)**:自主 EM 12/24;**闭卷对照不可用**——关掉检索后 13/20 是格式崩溃,测的是 ReAct 格式而非参数化记忆。
  → 改为"协议保持、检索一律返回空结果,两次空检索后必须 finish"。
- **v3**:闭卷修好,但**依赖资格只放行 2/24**,最大拒绝原因是"桥接实体出现在第一个观测里"(10/24)。
  **这是我写错了判据**:那恰恰是 HotpotQA 的标准两跳模式(搜电影页 → 读出导演 → 再搜导演),是要教的依赖,不该判不合格。
  → 改为:实体不在题面、只能经检索获得(第几次无所谓)、回答仍需一次**依赖该实体的后续检索**、起点不含 gold answer。
- **v4(最终口径,24 题)**:见下。

### 2.3 v4 结果
| 项目 | 数字 |
|---|---|
| 自主 EM | **12/24** |
| 闭卷 EM(强制作答) | **6/24** |
| 其中 凭记忆答对 / 答错 / 始终不答 | 6 / 18 / **0** |
| 检索成功而闭卷失败 | 7/24 |
| 答案首次出现在检索结果 | 11/23 |
| 答案字面出现在题面 | 4/24 |
| 重放:动作+观测一致 / 完全可复现 | 16/24 / 12/24 |
| 重放分歧归因 | 学生采样 11、记录不一致 1 |
| 缓存命中 | 88/88 |

**判定:测床合格。** 检索让正确率翻倍(12 vs 6),且没有"不肯收手"造成的假失败;题面直给只有 4/24。
重放完全可复现率 12/24 偏低,但分歧主要来自学生采样而非环境,教学素材可按记录重建。

## 三、第一阶段前提检验与失败定位(最重要)

### 3.1 前提是什么
新机制第一阶段的自变量是:**训练上下文是否保留了学生原本必须承担的选择**。
I 臂把前置信息直接写在上下文里,P 臂要求学生自己去获取。
我原本把"**交出前置信息会让任务变容易**"当作实验前提——**该要求已按评审删除**(见 §3.2 口径修订):
一次性帮助的价值与通过训练学会一种行为是两种不同的干预,前者为零推不出后者为零。

### 3.2 直接检验(v4,10 道合格题)
| 项目 | 数字 |
|---|---|
| 依赖资格合格 | **10/24**(不合格 14,原因已分类) |
| **独立练习提前交出关键实体** | **10/10** |
| 给定实体版成功 | **3/10** |
| 必须自检索版成功 | **3/10** |
| **"给定就会、必须自检索就不会"** | **0/10** |
| 两版都失败 / 都成功 | 7 / 3 |

结构上的主张成立且三次可重复(BFCL 6/6、HotpotQA 9/9、12/12、10/10):独立练习**确实**把关键实体提前交出去了。
行为上,给定实体并没有提高最终成功率(3/10 vs 3/10)。

**口径修订(2026-09-13 06:40 CDT,按评审)**:这条**不能**读成"前提不成立"。理由:
(a) **执行时给一次帮助 ≠ 通过训练学会一种行为**,两者是不同的干预(早期 ALFWorld 零 ΔU 示范仍有教学价值);
(b) 下游共同失败会**遮住上游改善**——最终 EM 相同不代表中间决策没有改善;
(c) 因此"交出前置信息必须让任务变容易"**不应作为实验前提**,该要求已删除。
同样要收窄的是 13/13:实体出现在 observation 里只说明**信息可见**,不能证明学生已经识别、选对并正确使用了它。
本次证据最可靠的表述是:**环境返回相关信息之后,学生仍然经常无法完成后续执行**——这正是"证据如何转化为行动"的问题。

### 3.3 失败定位(13 个可用配对,离线统计已保存记录,无额外 GPU)
| 失败类型 | 必须自检索版 | 给定实体版 |
|---|---:|---:|
| 成功 | 5 | 5 |
| **拿到实体之后仍答错** | **8** | 5 |
| 答案错误 | 4 | 3 |
| 触步数上限 | 4 | 5 |
| 动作格式错误 | 3 | 4 |
| 连实体都没观察到 | 0 | 3 |
| **实体是否检索到** | **13/13** | 10/13 |

**可靠结论:环境已经返回相关信息之后,学生仍然经常无法完成后续执行**(8/13 属于"实体已在 observation 中出现但最终答错")。
**不可推出**"学生已经掌握了获取实体这一步":实体可见不等于被识别与正确使用;也**不可**据此锁定"第二跳就是痛点"。
真正待研究的问题是统一的:**学生如何根据已经获得的信息作出下一项有用的决策。**

### 3.4 由此得到的判断(2026-09-13 06:40 CDT 修订)
**不是"前提被否定",而是"这次的检验设计问错了问题"**:它测的是**一次性帮助**对最终成功率的影响,
而我们真正要问的是**通过训练能否学会某种行为**。两者不同,前者为零不能推出后者为零。
可以确定的是:**失败大量发生在"信息已经返回之后"**,所以教学对照应当覆盖"证据 → 下一步决策"这一整段,
而不是只操纵"前置信息是给定还是自取"。BFCL 修复后 C→D 的零差异与此并不矛盾,两者都指向同一件事:
当前的练习构造没有针对学生真正失败的环节。

## 四、下一步(2026-09-13 06:40 CDT 定稿,按评审)
两条线**并行**;六个 adapter 等样本定义冻结、对照成立后再起,**不必等注意力先出正结果**。

**路线 1 — 教学对照(目标覆盖必须匹配)**

| 臂 | 监督内容 |
|---|---|
| **I′:拆开教完整操作集合** | 分别教后续查询、证据使用、答案与结束 |
| **P′:保留证据到行动的联系** | **相同的操作目标**,在真实交互上下文中教学 |
| **L′:普通连续片段** | 按事先冻结的截取协议,提供相近规模的合法交互教学 |

**明确禁止**我先前提的那版("I′ 只教最终答案、P′ 同时教检索和答案"):那样 P′ 的收益可能只是**多了检索监督**,
而 L′ 也补救不了这个混杂。两臂必须**操作目标覆盖与曝光都匹配**,并标出实际前缀的差别;
若只是把相同条件下的训练样本重新分包,就没有机制差异,不跑。
也**不事先锁定**"第二跳一定是痛点",让真实失败决定教什么;统一的问题是:
**学生如何根据已经获得的信息,作出下一项有用的决策。**

**路线 1 的前置诊断(现在做,不新增教师购买,不筛到出现预期差异)**:用全部合格案例,从日志区分四种可观察情况——
① 相关实体已出现但下一次查询没正确使用它(observation → 查询构造);② 查询合理但没取得有效结果(结果 → 检索调整);
③ 证据已充分但答案仍错(多段证据 → 答案);④ 已具备回答条件仍循环或无法结束(任务状态 → 正确结束)。
允许"日志不足以判断";失败可多标签;同时记录**最早的可观察偏离点**。必要时补三个小型推理条件(自然续接 / 后续证据已取得 / 相同证据直接作答),
它们是**诊断性辅助**,不作为新方法的正式评测分数。

**路线 2 — 离线读取诊断(立即做)**:四个条件同一冻结表示、相同可用资料与输出预算——
N 无 support;O 正确 support 一次读取;R 正确 support 递归读取;M support 对应关系受扰动(**明确标注为人为机制消融**;
同分布重抽另一组 support 属于抽样稳定性测试,不叫错配)。
指标改名并新增一项:**已标注相关证据遗漏率**、固定读取预算下的证据覆盖、无关内容比例、
**对学生实际失败位置的覆盖情况**。HotpotQA 的 supporting facts 不是唯一正确路径,不称"必要证据"。
关键判读:若读取器总选中学生**已经成功获取**的实体,却遗漏"如何据此形成下一查询",即使相关性分数好看,也没有对准教学问题。

**两条线共享的教学接口**:读取器输出单位 = **真实学生状态 + 相关证据及来源 + 学生实际采取的后续行动 + 观察到的执行结果**;
教师据此构造短练习。练习起点**不得**预填正确的下一查询或未来 observation。
时间边界:教学决策发生在一次 rollout 完成之后,选择器可以用完整记录做诊断,但给学生的练习必须保持正确的历史前缀;
未购买的教师输出、确认题答案与评分标注**不得**进入读取器。
若 R 不超过 O,就先用一次读取;若检索覆盖改善而学习收益没有改善,就继续修改教学接口。

判读仍按预登记:先看自主完成率,再看条件变化适应,最后才看完整任务与损伤;先按 parent 聚合再配对,单列每个种子;
塌缩或截断的运行照常报告(状态、截断比例、完成覆盖率),不报子集准确率,不挑 checkpoint。

**不做**:直接删掉 base 已正确的 token 只训练剩下部分(argmax 一致无法区分"无用语法"与"重要决策",
且重新归一化会放大每个位置的更新);也不在第一阶段结论出来前扩到别的 benchmark。

## 五、过程中发现并修复的工程问题(与结论无关但影响吞吐)
1. **终止监督缺失**(见 §1.1),已修。
2. **共享 run 目录 = 全局串行**:`mech_bfcl.py` 用一把 flock 包住整个 train/evaluate,9 个作业共用一个 run 目录时被完全串行化
   (1.5 小时只训完 1 个臂,其余占着 GPU 等锁)。改为每臂一个 run 目录(输入硬链接共享)。
3. **评测端口锁跨节点串行**:所有格子用默认端口 8930,而端口锁文件在共享文件系统上,**不同节点的作业也互相等锁**。
   改为按作业号分配端口。
4. **单文件 safetensors 无法导出**:合并导出工具要求分片 index,而 gemma-4-12B 快照是单文件 23.9 GB,BFCL 全部格子评测必挂。已支持单文件。
5. **跨机迁移不能拷 .venv**:解释器软链指向源机路径,导致重建作业 1 秒失败;每个 benchmark 的 venv 必须在目标机重建(bfcl / alfworld / vllm-serve 三处都踩过)。
6. **种子后缀重复**:跑器自己会加 `_s<seed>`,脚本重复添加导致 seed 1/2 的格子每次都撞"run-dir 已存在"。已修,并让聚合脚本同时认两种写法。
