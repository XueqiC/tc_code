\section{Methodology}\label{sec:method}
\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{figs/fig1_mechanism.pdf}
\caption{The pipeline in four stages. \textbf{Stage I} determines
the task from its few examples, where one backward pass turns each support
example into a gradient feature, and a two-view coupled dictionary
yields capability atoms (Definition~\ref{def:atom}), a task demand
(Definition~\ref{def:demand}) with per-capability token quotas, and the
task boundary as what this vocabulary can express. \textbf{Stage II}
acquires the data the specification asks for, running a loop that buys where unmet
quota is largest, filters every return through an execution check and
the membership test, and lets the student attempt candidates before
money is spent. \textbf{Stage III} distills the student on-policy, where the
training signal is stratified by the student's own policy state and
optimized as one verifier-anchored objective, finished with weight
averaging of near-best probe checkpoints. \textbf{Stage IV} certifies
the result, attaching a conformal gate with finite-sample two-sided certificates that
routes live requests.}
\label{fig:pipeline}
\end{figure}

In this section we first formulate the problem of producing a student
whose capability gap to a task revealed by only $k$ examples is
minimized under a token budget. We then propose \methodname{}, a
four-stage pipeline for this problem. As shown in
Figure~\ref{fig:pipeline}, we first determine what the task is from
its few examples by fitting one dictionary whose readings supply every
later coordinate, then acquire training data by a single marginal-value
rule that weighs gain on unmet demand against displacement of what the
student already has, then distill by one objective that executes the
labels acquisition wrote, and finally certify how well the student
matches the specification. The details of the proposed method are
below.

\subsection{Problem formulation}\label{sec:setting}

We first need to identify the task 
Let a task $\mathcal{T}$ be defined by its query distribution
$P_\mathcal{T}$, given a support set
$S = \{q_1, \dots, q_k\} \sim P_\mathcal{T}$ of example queries
with $k \ll N_{\mathrm{train}}$, the corpus size that could train the
student directly, a teacher agent
$\pi_T$ accessed as a black-box API that charges per emitted token, an
open-weight student $\theta_0$, and a token budget $b$, the goal is
\[
\hat{\theta} \;=\; \argmax_{\theta}\;
\mathbb{E}_{q\sim P_\mathcal{T}}\big[\,\mathrm{Perf}(\theta;
q)\,\big]
\quad \text{s.t.} \quad \mathrm{Cost}(\theta) \,\le\, b,
\]
where $\mathrm{Perf}(\theta; q)$ is the task performance of the
student on query $q$, and $\mathrm{Cost}(\theta)$ counts every
teacher token purchased while producing $\hat{\theta}$.

\subsection{Determining the task from its examples}
\label{sec:atoms}
We first need to identify what the task is
and what capability a model must hold to finish it. Our intuition is
that the gradient an example induces on the student records exactly
what the student would have to learn from it \citep{xia2024less}, so
we first run one backward pass per support example to obtain gradient
features, and then factor these features to identify the minimal set of
capabilities a model needs to perform the task well. In this way, the
capability to finish the task decomposes into a sparse combination of
\emph{capability atoms} (Definition~\ref{def:atom}). The same decomposition then tells
us how much of each capability the task demands
(Definition~\ref{def:demand}), it identifies the boundary of the task
as the set of queries this capability vocabulary can express, and it
forecasts how training on this task will affect any reference off-task,
since the two views of the dictionary measure prompt confusability and
response interference separately. One fitted object thus supplies every
coordinate the later stages consume, and nothing else is learned.

\paragraph{Gradient features.}\label{sec:fingerprints}
The first step needs a representation under which examples that teach
the same thing look alike. Text cannot provide such a representation,
because identical query texts solved in two different styles demand
different learning, yet no function of the text can tell them apart. The gradient can. The
gradient an example induces at the student's initialization records
what this student would have to learn from it, so every example the
method touches is represented by its \emph{gradient feature}
\citep{xia2024less}, defined as the Adam-preconditioned gradient of a
low-rank adapter, compressed by a fixed random projection that preserves the
inner products all downstream computation consumes
\citep{johnson1984extensions}. Each example yields two views. The
\emph{response view} is computed on a teacher solution and carries how
the example is solved; it exists only after the solution is paid for.
The \emph{prompt view} is computed on the question text alone and is
available before any purchase. The stages below plan with the prompt
view and account with the response view.

\paragraph{Capability atoms.}
The second step turns features into named capabilities. Gradient features of
related examples reuse a small set of recurring directions, the way
recipes reuse a small set of basic operations, and sparse dictionary
learning \citep{olshausen1996emergence} recovers such structure.
Sparsity is what makes the recovery meaningful, because a principal subspace is
invariant to rotations of its basis and cannot attach identity to any
single direction, while rotation destroys code sparsity, so only
recurring, self-contained gradient patterns survive the penalty. One
further requirement comes from the metered protocol. Which capabilities a
question exercises must be estimable before its answer is bought, so
the capability code of an example should not depend on which view of it is
visible. We therefore treat the prompt and the response as two
projections of one latent capability profile and learn a \emph{two-view
coupled dictionary} \citep{yang2010coupled}. Writing the prompt-view
and response-view feature matrices as $X_p$ and $X_r$, we solve
\[
\min_{D_p, D_r, C}\ \lVert X_p - CD_p\rVert_2^2
+ \lVert X_r - CD_r\rVert_2^2 + \lambda\lVert C\rVert_1,
\]
so a single sparse code per example must reconstruct both of its views.

\begin{definition}[Capability atom]\label{def:atom}
A \emph{capability atom} is one row $[d_p; d_r]$ of the learned coupled
dictionary, that is, a paired direction in prompt- and response-view
gradient-feature space. The sparse code $c(x)$ of an example is its
coefficient vector over the atoms; $|c(x)|_a$ measures how strongly
example $x$ exercises atom $a$, and for a candidate whose response has
not been purchased it is computed from the prompt view alone, by a
lasso solve against the $D_p$ block.
\end{definition}

The shared code is what removes the need for any learned bridge between
views. Support demonstrations are free and purchased examples
accumulate, so response information shapes the dictionary at fit time,
and a candidate's prompt-only code inherits it. Because no corpus is
given, the dictionary cannot be pretrained. It is instead fit on the
support set first and refit as purchases accumulate, so the vocabulary
sharpens with evidence.

\paragraph{Task demand and quotas.}
With the vocabulary in hand, the third step reads off how much of each
capability the task actually wants.

\begin{definition}[Task demand]\label{def:demand}
Given a dictionary and the support set $S$, the \emph{task demand} is
$w = \frac{1}{k}\sum_{q\in S} |c(q)|$, normalized to sum to one and
restricted to the atoms carrying $90\%$ of its mass. Scaled by the
budget, $w \cdot b$ assigns each atom a token quota.
\end{definition}

The support set is a small sample, so $w$ inherits its blind spots. The
teacher's own solutions correct part of them, since atoms that appear
persistently in the codes of demonstrations for support queries, yet
carry little weight in $w$, are capabilities the task requires
\emph{implicitly}, and their demand is filled in from the demonstration
side before further budget is spent. This completion touches only the
budget allocation; the boundary and all certificates remain calibrated
on the original $k$ queries alone. The same vocabulary also defines
where the task ends. A query belongs to the task exactly when the capability
vocabulary can express it, so the reconstruction residual of a prompt
under the $D_p$ block, thresholded at the least typical calibration
query, is the boundary; Stage II uses it to filter purchases and Stage
IV calibrates it into a certificate.

\subsection{Budgeted data acquisition}
\label{sec:acquire}

After Stage I, we can now acquire the data from which the student will
be distilled, and the entire stage is one decision rule. For each
candidate supervision action $a$, whether buying a demonstration,
buying a minimal correction of a failed attempt, keeping a self-solved
trajectory, or stopping, the dictionary readings estimate a marginal
net value
\[
v(a) \;=\; \underbrace{\frac{\sum_{c} \min\big(r_c,\
\hat{s}_c(a)\big)}{\hat{t}(a)}}_{\text{gain on unmet demand}}
\;-\;
\underbrace{\lambda_{\mathrm{anc}}\,\Delta_{\mathrm{anchor}}(a)
\;+\; \sum_{c\in\mathrm{shared}} \hat{s}_c(a)\,
\kappa^{r}_{c}}_{\text{displacement cost}},
\]
where $r_c$ is the remaining allocation of atom $c$, $\hat{s}(a)$ is
the prompt-view code of the candidate, $\hat{t}(a)$ its expected token
cost, $\Delta_{\mathrm{anchor}}$ the dilution of the student's own
verified rows in the training mix, and $\kappa^{r}$ the response-view
coupling of shared atoms. Acquisition simply executes
$\argmax_a v(a)$ each round and stops spending once every action has
$v(a) \le 0$.

Every component of earlier pipelines becomes a consequence of this one
rule rather than a module of its own. A self-solved trajectory costs
nothing, so its value per token dominates and the student is always
attempted first. The $\min(r, \cdot)$ truncation is exactly the
concave cap that makes the implicit coverage objective monotone
submodular, so greedy selection inherits the classical
near-optimality guarantee \citep{khuller1999budgeted, krause2005near}.
The membership gate stops being a module at all and becomes a
proposition. An out-of-task prompt receives near-zero code mass on the
demanded atoms, because sparse coding assigns magnitude only where the
vocabulary can reduce reconstruction error, so its gain term vanishes
and the rule never selects it; the execution check remains only to
verify delivered goods, and rejected purchases are reported as waste.
Corrective rounds, the shift from demonstrations toward corrections,
and the eventual halt all emerge as the student's state evolves,
because unmet demand decays, failures concentrate, and the
displacement cost of further cloning rises. The rule has no round
structure, no dose constants, and no phase boundaries.

\subsection{Distilling the student}
\label{sec:distill}
Stage III makes no decisions of its own; it executes the ledger that
acquisition already wrote. Every training row arrives labeled by whose
behavior it records, and a single objective reads those labels,
\[
\mathcal{L}(x) \;=\; \mathrm{NLL}\big(y^{+}\,|\,x\big) \;+\;
\beta\,\mathbb{1}\big[y^{-} \text{ exists}\big]\cdot
\ell_{\mathrm{OR}}\big(y^{+}\!\succ y^{-}\,|\,x\big).
\]
Rows holding the student's own verified solutions are trained as plain
likelihood, preserving the behavior being kept at zero teacher cost in
the spirit of self-improvement bootstrapping \citep{zelikman2022star};
they are the anchor of the mix, and their share was already protected
by the displacement term at purchase time, so training needs no
protective patches. Rows carrying a paired failure add the preference
term $\ell_{\mathrm{OR}}$, a reference-model-free odds ratio
\citep{hong2024orpo} since the teacher exposes no log-probabilities.
The pair is admissible only when its two sides diverge on the
\emph{success axis}, meaning the verifier scores them differently;
pairs that diverge merely in style are refused, because pushing down a
stylistic variant of correct behavior trains exactly the drift the
anchor exists to prevent. The term activates on a row only after that
row's positive solution has been learned, gated by the running mean
likelihood, and it is computed only from the first token of divergence,
which removes likelihood-displacement pressure at its source
\citep{razin2025unintentional}. All remaining rows are plain behavior
cloning, the degenerate repair of an empty attempt. Training ends with
weight averaging of near-best probe checkpoints \citep{izmailov2018swa}
and a rollback that fires only past a one-probe-question margin; the
probe measures execution correctness, whose gold answers come free
from executing the teacher's demonstrations. Per-example losses,
tagged by dominant atom, aggregate into per-atom absorption curves at
no extra cost and feed the deficit reads of Stage II.

\subsection{Certification and deployment}
\label{sec:behavior}
Stage IV states, with finite-sample guarantees, how well the delivered
student matches the specification, and then holds the student to it at
deployment. A deployment-time request carries no response, so the
boundary predictor lives in prompt-feature space and reuses the same membership machinery estimated in Stage I. The
reconstruction residual under the $D_p$ block is the nonconformity
score, and a conformal
threshold from a disjoint calibration split gives distribution-free
coverage $\ge 1-\alpha$ \citep{angelopoulos2023conformal}. The student is then
evaluated behaviorally on both sides of the boundary and the capability
match is stated as finite-sample Clopper--Pearson bounds, giving a
certified lower bound on in-task coverage and a certified upper bound
on off-task leakage, which is a bounded claim rather than a score. At deployment the same machinery gates live requests, routing
in-specification queries to the student and refusing or escalating the
rest to the teacher, so the certificates describe exactly the traffic
the student will see.
